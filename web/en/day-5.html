Day 5 · 60 minutes · EXPLAIN, DISCUSS, TRANSFER

Demonstration, Discussion and Feedback

Turn four days of building and testing into a concise professional explanation: what educational problem the prototype addresses, what the agent actually does, what evidence supports its behaviour, where its limits remain, and what you would do next.

No major new build · evidence + reflection + transfer
Day 5 boundary: do not create a new feature simply to make the demonstration more impressive. Demonstrate the final tested version from Day 4. If you change instruction, configuration or code, the required Day 4 T1–T3 set must be rerun before the new version is described as tested.

Learning goals

Explain purpose before technology

Start with the learner/instructor need, then explain how the prototype supports it.

Show evidence, not claims

Use one real tool/log item and the final T1–T3 record rather than saying only “the agent works.”

State limits without hiding them

Identify one human-control point and one condition not validated by this workshop.

Transfer the pattern

Respond to one new condition by explaining what would change and what would need retesting—without live coding.

Give actionable feedback

Separate workshop-content feedback, technical blockers and your own next-step idea.

1. Reopen the final tested version

Before presenting, confirm that the configuration and evidence belong to the same final Day 4 version.

Version

Know the local checkpoint/commit or other clear identity of the version you are showing.

Tool evidence

Have one real read_course_material log entry ready to show without exposing secrets.

Test evidence

Have the final T1, T2 and T3 results from that same version.

Limitation

Bring one concrete human-control or validation limitation rather than a generic “AI can make mistakes.”

2. Three-minute demonstration structure

A strong demonstration is a short argument, not a tour of every file. Use this order:

Problem
What learner/instructor action needs support?
Prototype
What does the agent do—and what does it not do?
Bounded change
What one participant-controlled change did you make?
Real action
Show one factual tool/log record
Tests
Summarise final T1–T3 results
Limitation
Where is human judgment still necessary?
Next step
What would you validate or adapt next?

4. One new condition — transfer without live coding

After the demo, the instructor gives one new condition. Your answer should follow a four-part structure:

  1. What changes? Identify the part of the educational design or application that is affected.
  2. What stays fixed? Preserve the safety/data/tool boundaries unless the institution explicitly redesigns and revalidates them.
  3. What would you modify? Name the smallest plausible change.
  4. What must be retested? Explain which previous evidence becomes stale after the change.

Condition A — only 8 minutes

Shorten the learning workflow; do not simply ask the model to produce more work for the learner. Revalidate timing and learner-first behaviour.

Condition B — less experienced learners

Increase scaffolding/focused questions while preserving an independent learner contribution. Retest T3-like authorship boundaries.

Condition C — two approved sources

The current one-material boundary is no longer sufficient. Source selection/tool logic and grounding tests would need redesign and validation.

Condition D — no cloud provider

Saved evidence can support explanation, but live inference is unavailable. A local inference route would need separate setup and validation before being treated as equivalent.

Condition E — restricted material

Do not put it into the current cloud workshop route. Data boundary, local/institutional infrastructure and approval requirements would need a separate design.

Mini-check — what becomes stale?

You substantially change the instruction for a new learner group. Can you still cite the old T1–T3 record as proof of the new version?

5. Discussion — where is an agent actually the right tool?

Good candidate

A repeated educational workflow has a defined learner/instructor action, clear evidence sources, bounded tools and observable outputs.

Maybe just use a chatbot

The task is a one-off explanation or brainstorming conversation and no controlled external action/source workflow is needed.

Maybe use static material

The learner only needs a fixed explanation, checklist or reference and adaptive behaviour adds little value.

Stop / redesign first

The task would require sensitive data, poorly defined responsibility, unbounded external actions or a level of reliability not validated by the prototype.

The common thread is human control over increasingly capable workflows: first understand, then change software safely, then build a bounded agent, then test it, then explain when the pattern should or should not be reused.

7. Feedback — make it actionable

Use the approved feedback route. Do not include API keys, project secrets, sensitive information or private execution logs.

  1. Value: Which part most improved your ability to understand or work with AI agents?
  2. Clarity: Which concept or task was least clear?
  3. Pacing: Which day needs more time? Which could be shorter?
  4. Technical friction: What blocker consumed the most time?
  5. Transfer: What educational-agent use case would you try next?
  6. Confidence: Which action can you now perform independently: run / change / inspect tool evidence / test / explain?
  7. Instructor improvement: What is the one change that would most improve the next delivery?

8. Choose one realistic next step

A next step should be small enough to validate. Choose one:

Refine this prototype

Improve the same single-agent learning workflow using evidence from testing and feedback.

Adapt the pattern

Use the same bounded architecture for another public/synthetic educational case and create a new test set.

Plan an institutional pilot

Define approved data, infrastructure, responsibilities, support and acceptance evidence before real learner use.

Stop deliberately

Document why the use case does not justify an agent. Choosing not to automate can be a valid outcome.

Advanced RAG, multi-agent systems, MCP/A2A, broad tool access and production deployment remain outside the five-day pilot unless a later course/revision explicitly introduces them.

Final checkpoint

Demonstration

Educational problem → prototype → bounded change → real action evidence → final T1–T3 → limitation.

Transfer

You answered one new condition by stating what changes, what stays fixed and what must be retested.

Feedback

You gave actionable feedback through the approved route without sharing secrets/sensitive data.

Next step

You named one realistic continuation—or a deliberate stop—and the validation needed before real learner use.

Workshop outcome: you are not expected to become a software engineer. You should now be able to explain what an agentic educational application is, use AI to make controlled software changes, inspect a simple agent’s real action, change one bounded behaviour, test important boundaries, and communicate the prototype’s educational value and limitations.
