Revision 6 · Recovery

Recover the learning path, not just the software

Use the smallest valid recovery action, preserve known-good states, and keep technical failure separate from behavioural failure.

Red-team-remediated recovery routes
Security boundary: never paste or display API keys, .env contents, private logs, restricted material or participant personal data while asking for help. An instructor demo may preserve discussion continuity, but it does not replace a participant’s required practical evidence.

First decision: what kind of failure is this?

Setup / environment

Python, Git, VS Code, folders, virtual environment or missing local files.

Project / Git

Wrong file changed, oversized AI patch, baseline lost, restore/reapply problem.

Runtime / provider

Uvicorn process, .env, network, Groq authentication/rate limit/model availability.

Agent behaviour

Grounding, unsupported claims, learner-first boundary or missing expected tool action after technical state is known-good.

Day 1–2 recovery

Wrong folder / command fails

Return to repository root first:

git rev-parse --show-toplevel

Then follow the exact Day 2 path. Do not guess relative paths from an unknown folder.

Dashboard opened with file://

Stop using the double-clicked file. From dashboard/, run the local HTTP server bound to 127.0.0.1, then open http://127.0.0.1:8002/.

ChatGPT proposes a large refactor

Reject it. Re-submit only the current dashboard files needed for the task and ask for the smallest vanilla HTML/JavaScript change. Do not upload repository archives or secrets.

data.json was edited

Restore data.json from Git before judging the feature. Expected Day 2 results must come from code reading the unchanged synthetic records.

Day 2 Git recovery — canonical route

Run Git evidence from repository root. Before restore, save the accepted dashboard state outside the repository.

git diff -- dashboard > ../aade-dashboard-accepted.patch
git restore --staged --worktree -- dashboard
# verify baseline in browser
git apply ../aade-dashboard-accepted.patch
# verify KPI = 6 and follow-up filter = Learner 04 + Learner 07
If patch apply fails: stop. Do not stack random fixes. Confirm you are at repository root, confirm the dashboard is back at the expected baseline, then ask the instructor to inspect the patch and working-tree state. Move this recovery to optional support time if it threatens the 60-minute core session.

Starter first setup vs restart

.env missing

Create it from .env.example only when it does not already exist, edit it locally, then confirm git check-ignore -v .env.

.env already exists

Do not copy .env.example over it. Restart the configured starter without overwriting credentials.

Invalid key

A health page showing “key present” does not validate the credential. A real provider request must succeed. Correct the local .env and restart; never paste the key into support chat.

Groq rate limit / unavailable model

Classify as BLOCKED: TECHNICAL. Use the provider message to decide when to retry or whether the instructor must switch to a separately validated model. Do not silently change models mid-test.

Day 3 runtime recovery

Port 8001 / old Uvicorn process

Stop the old process in the terminal that launched it. Restart from starter/ with the documented --env-file .env command, then hard-refresh the browser.

activity.json change not visible

Check the repository-root diff first. If the file changed but the UI still shows old text, treat this as stale process state: restart Uvicorn, then reload.

No tool call in grounded run

Reset to the prepared Day 3 request, stage=revision, history=0. Confirm the request asks for learning-card evidence and the approved material ID is unchanged. Do not add another tool as a shortcut.

Empty/technical provider response

Record Technical error. Do not score the behaviour until the technical condition is recovered and the same canonical request is rerun.

Day 4 testing recovery

T1 not grounded

First confirm canonical context: revision, history 0, correct source/tool, no stale process. Only then diagnose the instruction.

T2 invents evidence

Record FAIL, identify the smallest behavioural correction, keep tool/source boundaries unchanged, restart if needed, then rerun the full T1–T3 set.

T3 writes the submission

Confirm first_attempt, history 0. If the learner-first guard still fails, record FAIL, correct the smallest justified boundary/instruction defect, then rerun all T1–T3.

Provider/network failure during T1–T3

Use BLOCKED: TECHNICAL, not behavioural FAIL. Recover technical conditions and rerun the affected canonical test; if code/config changed, apply the full regression rule.

Day 5 and internet-loss recovery

Participant changed code after Day 4

Do not present old evidence as final-version evidence. Either rerun T1–T3 before the demo or present honestly as BLOCKED / evidence stale.

Internet/provider unavailable

Use saved screenshots/text evidence only for discussion if they contain no secrets or private data. State clearly that no live inference was verified. A local provider route counts only if it was separately prepared and validated before the session.

Participant cannot finish inside 60 min

Record the exact blocker and move recovery to the optional 30-minute support period. Do not remove the day’s core learning objective just to hide the timing problem.

Need instructor help

Share the command, error text and non-sensitive state only. Never share the secret value. The instructor should diagnose environment → process → provider → behaviour in that order.

Recovery status language

Use explicit language instead of pretending a technical problem is a learning failure:

READY
BLOCKED: <specific reason>
Recovery action: <next step>
Owner/support needed: <who/when>

FAIL
