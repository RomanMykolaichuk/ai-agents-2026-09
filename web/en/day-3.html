Day 3 · 60 minutes · BUILD AN AGENT

Building an Educational Agent

Launch the prepared runtime from a known folder, trace the real request → model → tool → source → response/log pipeline, make your own learner attempt, observe one factual tool action, then change one instruction and compare the result.

Canonical participant path · RT-FIX-1
Day 3 boundary: build and understand the existing educational agent. Formal T1–T3 verification remains Day 4. Do not add tools, frameworks, RAG, memory, web access or new architecture.

1. Canonical launch path

Where am I?

Start inside the repository, then enter starter/. Keep the server terminal open while using the browser.

What must already exist?

.venv, pinned dependencies, successful verify.py, and local ignored .env from Day 2.

What should I see?

At http://127.0.0.1:8001/: activity, learning card, current instruction/configuration, learner stage, response and execution evidence areas.

If launch fails?

Fix folder/environment/provider setup first. Do not edit activity.json while the known-good runtime itself is broken.

Windows PowerShell — launch

Set-Location (git rev-parse --show-toplevel)
Set-Location workshops\ai-agents-defence-education\starter
.\.venv\Scripts\python.exe verify.py
.\.venv\Scripts\python.exe -m uvicorn app:app --host 127.0.0.1 --port 8001 --env-file .env

Ubuntu/Linux — launch

cd "$(git rev-parse --show-toplevel)/starter"
.venv/bin/python verify.py
.venv/bin/python -m uvicorn app:app --host 127.0.0.1 --port 8001 --env-file .env

2. Trace the actual agent pipeline

User request
Learner asks for bounded help
Application rules
Task, instruction, stage, limits and allowed material
Model call
Model interprets the request within those rules
Approved tool
read_course_material can read only the allow-listed card
Observation
Tool result returns to the application/model context
Final response
Bounded learner support
Factual log
Records what the application actually did
Evidence rule: “the model says it used the source” is not proof. Tool name + material ID + result in the application execution log is execution evidence.

3. Know what you may and may not change

task

Defines the educational problem. Read it; do not change it in the core Day 3 exercise.

instruction

The one participant edit surface for the core exercise. It shapes support behaviour without adding capability.

hint_question

Visible support wording. Keep unchanged during the core comparison so the instruction is the main changed variable.

allowed_material_id

Fixed source boundary. Do not change it or add arbitrary file/URL access.

4. Make your independent first attempt

Read Learning Card A–C in the starter and write your own teaching-format choice before asking the agent. Include two card-based reasons and one limitation. The agent is supposed to support revision, not replace the learner’s reasoning.

5. Run one grounded request

Use the starter’s prepared Load grounded request control, then send it to the agent. For this Day 3 canonical path, use the prepared control rather than manually retyping the test prompt. After the response, inspect the execution log first.

Expected normal status

Completed when the provider/runtime completes normally.

Expected tool evidence

One read_course_material call with material ID leadership-card-a-c.

Expected answer boundary

Short card-grounded support that leaves the learner as author and does not invent evidence.

Expected limits

Tool/model call counts remain within the displayed runtime constraints.

6. Change one instruction only

Use ChatGPT Plus only for bounded wording support. Copy the current instruction text—not .env, not the API key—and use the canonical prompt below. Then manually edit only the instruction value in starter/activity.json.

Reject: proposals that change task, hint_question, allowed_material_id, Python code, tools, routes, dependencies, memory, RAG, web access or other capabilities.

7. Inspect the exact file change from repository root

Windows PowerShell

Set-Location (git rev-parse --show-toplevel)
git status --short
git diff -- starter/activity.json

Ubuntu/Linux

cd "$(git rev-parse --show-toplevel)"
git status --short
git diff -- starter/activity.json

PASS this step only if the diff changes the instruction text and no other field.

8. Restart and compare the same request

  1. Stop the running Uvicorn process with Ctrl+C.
  2. Run the same launch command again from starter/.
  3. Hard-refresh http://127.0.0.1:8001/.
  4. Confirm the revised instruction is visible.
  5. Use the same prepared grounded request again.
  6. Compare grounding, learner authorship, usefulness and real tool/log evidence.

A different response is not automatically better. It is acceptable to record NO MATERIAL IMPROVEMENT if the original wording already met the learning purpose.

9. Recovery

Old instruction still visible

Stop the old server process, relaunch with --env-file .env, then hard-refresh. Treat stale-process state as different from repository state.

No tool call

Use the prepared grounded request, check the fixed material ID and source configuration. Do not add another tool to force success.

Technical error

Check provider/model/local environment. Record a technical blocker; do not paste the API key into support chat.

AI proposes a large refactor

Reject it and restate: change only the instruction string; preserve all tools, files and hard runtime controls.

Canonical practice tools

Bounded instruction-improvement request

I will provide the current instruction string from activity.json. Explain what it currently asks the educational agent to do, then propose one clearer alternative that preserves learner authorship, uses the approved learning card when evidence is needed, avoids invented evidence, and keeps support short and focused. Change only the instruction wording. Do not change task, hint_question, allowed_material_id, tools, files, Python code, routes, packages, memory, RAG, web access or any capability.
