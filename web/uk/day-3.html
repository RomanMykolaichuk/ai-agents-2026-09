День 3 · 60 хвилин · BUILD AN AGENT

Створення освітнього агента

Запустіть підготовлений runtime із відомої папки, простежте реальний pipeline request → model → tool → source → response/log, зробіть власну learner attempt, побачте factual tool action, а потім змініть одну instruction і порівняйте результат.

Канонічний маршрут учасника · RT-FIX-1
Межа Дня 3: створюємо й розуміємо наявного educational agent. Формальні T1–T3 залишаються Днем 4. Не додавайте tools, frameworks, RAG, memory, web access чи нову architecture.

1. Канонічний запуск

Де я працюю?

Почніть усередині repository, потім перейдіть у starter/. Server terminal залишайте відкритим під час роботи в browser.

Що вже має бути?

.venv, pinned dependencies, successful verify.py і local ignored .env, підготовлені у День 2.

Що має бути видно?

На http://127.0.0.1:8001/: activity, learning card, current instruction/configuration, learner stage, response та execution evidence.

Якщо launch fails?

Спочатку виправте folder/environment/provider setup. Не редагуйте activity.json, доки known-good runtime сам не запускається.

Windows PowerShell — launch

Set-Location (git rev-parse --show-toplevel)
Set-Location workshops\ai-agents-defence-education\starter
.\.venv\Scripts\python.exe verify.py
.\.venv\Scripts\python.exe -m uvicorn app:app --host 127.0.0.1 --port 8001 --env-file .env

Ubuntu/Linux — launch

cd "$(git rev-parse --show-toplevel)/starter"
.venv/bin/python verify.py
.venv/bin/python -m uvicorn app:app --host 127.0.0.1 --port 8001 --env-file .env

2. Простежте фактичний agent pipeline

User request
Learner просить bounded help
Application rules
Task, instruction, stage, limits та allowed material
Model call
Model інтерпретує request у цих rules
Approved tool
read_course_material читає лише allow-listed card
Observation
Tool result повертається в application/model context
Final response
Bounded learner support
Factual log
Фіксує те, що application реально виконав
Правило evidence: фраза model “I used the source” не є proof. Execution evidence — це tool name + material ID + result у factual application log.

3. Знайте, що можна і чого не можна змінювати

task

Визначає educational problem. Прочитайте, але не змінюйте в core Day 3 exercise.

instruction

Єдина participant edit surface у core exercise. Вона змінює support behaviour, не додаючи нової capability.

hint_question

Залиште без змін у core comparison, щоб instruction була головною changed variable.

allowed_material_id

Фіксована source boundary. Не змінюйте її і не додавайте arbitrary file/URL access.

4. Зробіть власну першу спробу

Прочитайте Learning Card A–C у starter і до звернення до agent запишіть власний teaching-format choice: два card-based reasons і одне limitation. Agent має підтримати revision, а не підмінити learner reasoning.

5. Виконайте один grounded request

У starter використайте prepared control Load grounded request, а потім send to agent. Для canonical Day 3 path використовуйте саме prepared control, а не ручне передруковування test prompt. Після response спочатку перевірте execution log.

Expected normal status

Completed, коли provider/runtime завершився нормально.

Expected tool evidence

Один read_course_material call із material ID leadership-card-a-c.

Expected answer boundary

Коротка card-grounded support, яка залишає learner автором і не вигадує evidence.

Expected limits

Tool/model call counts залишаються в межах displayed runtime constraints.

6. Змініть лише одну instruction

Використовуйте ChatGPT Plus тільки для bounded wording support. Скопіюйте current instruction text — не .env і не API key — та застосуйте canonical prompt нижче. Потім вручну змініть тільки instruction value у starter/activity.json.

Відхиляйте: proposals, що змінюють task, hint_question, allowed_material_id, Python code, tools, routes, dependencies, memory, RAG, web access або інші capabilities.

7. Перевірте exact file change з repository root

Windows PowerShell

Set-Location (git rev-parse --show-toplevel)
git status --short
git diff -- starter/activity.json

Ubuntu/Linux

cd "$(git rev-parse --show-toplevel)"
git status --short
git diff -- starter/activity.json

Цей крок PASS лише якщо diff змінює текст instruction і жодне інше field.

8. Restart і compare того самого request

  1. Зупиніть running Uvicorn через Ctrl+C.
  2. Знову запустіть той самий launch command із starter/.
  3. Hard-refresh http://127.0.0.1:8001/.
  4. Підтвердьте, що revised instruction видима.
  5. Знову використайте same prepared grounded request.
  6. Порівняйте grounding, learner authorship, usefulness і real tool/log evidence.

Different response не означає automatic improvement. Допустимо зафіксувати NO MATERIAL IMPROVEMENT, якщо original wording already sufficient.

9. Recovery

Old instruction still visible

Stop old server, relaunch with --env-file .env, then hard-refresh. Stale-process state відрізняється від repository state.

No tool call

Використайте prepared grounded request, перевірте fixed material ID і source configuration. Не додавайте another tool як shortcut.

Technical error

Перевірте provider/model/local environment. Зафіксуйте technical blocker; не вставляйте API key у support chat.

AI пропонує великий refactor

Відхиліть його: change only instruction string; preserve all tools, files and hard runtime controls.

Канонічні інструменти практики

Bounded instruction-improvement request

I will provide the current instruction string from activity.json. Explain what it currently asks the educational agent to do, then propose one clearer alternative that preserves learner authorship, uses the approved learning card when evidence is needed, avoids invented evidence, and keeps support short and focused. Change only the instruction wording. Do not change task, hint_question, allowed_material_id, tools, files, Python code, routes, packages, memory, RAG, web access or any capability.
