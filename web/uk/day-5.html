День 5 · 60 хвилин · EXPLAIN, DISCUSS, TRANSFER

Демонстрація, обговорення та фідбек

Перетворити чотири дні створення й тестування на коротке професійне пояснення: яку educational problem вирішує prototype, що agent реально робить, який evidence підтримує його behaviour, де залишаються limits і що ви робили б далі.

No major new build · evidence + reflection + transfer
Межа Дня 5: не створюйте new feature лише для того, щоб зробити demonstration ефектнішою. Показуйте final tested version з Дня 4. Якщо змінюєте instruction, configuration або code, required T1–T3 set потрібно повторити до того, як називати new version tested.

Навчальні цілі

Пояснювати purpose до technology

Починати з learner/instructor need, а потім пояснювати, як prototype її підтримує.

Показувати evidence, а не claims

Використати один real tool/log item і final T1–T3 record замість фрази “agent works”.

Не приховувати limits

Назвати одну human-control point і одну condition, яку workshop не validated.

Переносити pattern

Відповісти на одну new condition: що зміниться і що треба retest — без live coding.

Давати actionable feedback

Розділяти workshop-content feedback, technical blockers і власну next-step idea.

1. Відкрийте final tested version

До presentation переконайтеся, що configuration і evidence належать одній і тій самій final Day 4 version.

Version

Знайте local checkpoint/commit або інший clear identity версії, яку показуєте.

Tool evidence

Підготуйте один real read_course_material log entry без secrets.

Test evidence

Майте final T1, T2 і T3 results саме від цієї version.

Limitation

Підготуйте concrete human-control/validation limitation, а не generic “AI can make mistakes”.

2. Структура трьохвилинної demonstration

Сильна demonstration — це короткий argument, а не tour усіх files. Використовуйте такий порядок:

Problem
Яка learner/instructor action потребує support?
Prototype
Що agent робить — і чого не робить?
Bounded change
Яку одну participant-controlled change ви зробили?
Real action
Покажіть один factual tool/log record
Tests
Стисло final T1–T3 results
Limitation
Де human judgment досі потрібний?
Next step
Що ви validated/adapted би далі?

Яким має бути first sentence сильної Day 5 demonstration?

4. Одна new condition — transfer без live coding

Після demo instructor дає one new condition. Відповідь має чотири parts:

  1. What changes? Визначте affected part educational design/application.
  2. What stays fixed? Зберігайте safety/data/tool boundaries, якщо institution окремо не redesign/revalidate їх.
  3. What would you modify? Назвіть smallest plausible change.
  4. What must be retested? Поясніть, який previous evidence стане stale.

Condition A — only 8 minutes

Скоротіть learning workflow; не перекладайте більше роботи на model замість learner. Revalidate timing + learner-first behaviour.

Condition B — less experienced learners

Збільшіть scaffolding/focused questions, але preserve independent learner contribution. Retest T3-like authorship boundary.

Condition C — two approved sources

Current one-material boundary already insufficient. Source selection/tool logic і grounding tests потребують redesign/validation.

Condition D — no cloud provider

Saved evidence можна показати, але live inference unavailable. Local inference route потребує separate setup/validation до claim of equivalence.

Condition E — restricted material

Не додавайте його в current cloud workshop route. Data boundary, local/institutional infrastructure і approvals потребують separate design.

Mini-check — який evidence стає stale?

Ви substantially change instruction для new learner group. Чи можна старий T1–T3 record називати proof нової version?

5. Discussion — де agent справді є right tool?

Good candidate

Repeated educational workflow має defined learner/instructor action, clear evidence sources, bounded tools і observable outputs.

Maybe just use a chatbot

Task — one-off explanation/brainstorming і controlled external action/source workflow не потрібний.

Maybe use static material

Learner потрібен fixed explanation/checklist/reference, а adaptive behaviour дає мало additional value.

Stop / redesign first

Task потребує sensitive data, poorly defined responsibility, unbounded external actions або reliability level, який prototype не validated.

6. Синтез усього workshop

Day 1 — UNDERSTAND
AI, LLMs, assistants, agents, tools, human control
Day 2 — CREATE WITH AI
controlled vibe coding + Git evidence/recovery
Day 3 — BUILD AN AGENT
pipeline, source/tool evidence, bounded instruction change
Day 4 — TEST AN AGENT
T1–T3, diagnosis, correction + regression rule
Day 5 — EXPLAIN & TRANSFER
demo, limits, new condition, feedback + next step

Common thread — human control over increasingly capable workflows: спочатку understand, потім safely change software, потім build bounded agent, test it, і нарешті explain when the pattern should or should not be reused.

7. Feedback — робимо його actionable

Використайте approved feedback route. Не додавайте API keys, project secrets, sensitive information або private execution logs.

  1. Value: Яка частина найбільше покращила вашу ability to understand/work with AI agents?
  2. Clarity: Який concept/task був найменш зрозумілим?
  3. Pacing: Якому day потрібно more time? Який може бути shorter?
  4. Technical friction: Який blocker забрав найбільше часу?
  5. Transfer: Який educational-agent use case ви спробували б next?
  6. Confidence: Що тепер можете виконати independently: run / change / inspect tool evidence / test / explain?
  7. Instructor improvement: Яка one change найбільше покращить next delivery?

8. Оберіть один realistic next step

Next step має бути достатньо малим для validation. Оберіть один:

Refine this prototype

Покращити same single-agent learning workflow на основі testing + feedback evidence.

Adapt the pattern

Використати same bounded architecture для іншого public/synthetic educational case і створити new test set.

Plan an institutional pilot

Визначити approved data, infrastructure, responsibilities, support і acceptance evidence до real learner use.

Stop deliberately

Зафіксувати, чому use case не виправдовує agent. Decision not to automate може бути valid outcome.

Advanced RAG, multi-agent systems, MCP/A2A, broad tool access і production deployment залишаються outside the five-day pilot, якщо later course/revision явно їх не вводить.

Фінальна контрольна точка

Demonstration

Educational problem → prototype → bounded change → real action evidence → final T1–T3 → limitation.

Transfer

Ви відповіли на one new condition: what changes, what stays fixed, what must be retested.

Feedback

Ви дали actionable feedback через approved route без secrets/sensitive data.

Next step

Ви назвали realistic continuation — або deliberate stop — і validation needed before real learner use.

Результат воркшопу: від вас не очікується, що ви станете software engineer. Ви маєте вміти пояснити agentic educational application, використати AI для controlled software changes, побачити real action простого агента, змінити one bounded behaviour, протестувати important boundaries і пояснити educational value та limitations.
