Редакція 6 · Відновлення

Відновлюємо навчальний маршрут, а не лише програму

Застосовуйте найменшу коректну дію відновлення, зберігайте відомі працездатні стани та не плутайте технічну помилку з поведінковою.

Маршрути відновлення після red-team аналізу
Межа безпеки: ніколи не вставляйте й не показуйте API keys, вміст .env, приватні логи, матеріали з обмеженим доступом або персональні дані учасників під час отримання допомоги. Демонстрація викладача може підтримати обговорення, але не замінює обов’язковий практичний доказ учасника.

Перше рішення: який це тип збою?

Setup / environment

Python, Git, VS Code, папки, virtual environment або відсутні локальні файли.

Project / Git

Змінено не той файл, надмірний AI patch, втрачено baseline, проблема restore/reapply.

Runtime / provider

Процес Uvicorn, .env, мережа, Groq authentication/rate limit/model availability.

Поведінка агента

Grounding, unsupported claims, learner-first boundary або відсутність очікуваної tool action після підтвердження працездатного технічного стану.

Відновлення День 1–2

Не та папка / команда не працює

Спочатку поверніться до кореня репозиторію:

git rev-parse --show-toplevel

Потім виконуйте точний маршрут Day 2. Не вгадуйте відносні шляхи з невідомої папки.

Dashboard відкрито через file://

Не використовуйте файл, відкритий подвійним кліком. З папки dashboard/ запустіть локальний HTTP server на 127.0.0.1 і відкрийте http://127.0.0.1:8002/.

ChatGPT пропонує великий refactor

Відхиліть його. Передайте лише актуальні dashboard files, потрібні для задачі, і попросіть найменшу зміну vanilla HTML/JavaScript. Не завантажуйте архів репозиторію або secrets.

Змінено data.json

Відновіть data.json з Git до оцінювання функції. Очікувані результати Day 2 мають обчислюватися кодом з незмінених synthetic records.

Day 2 Git recovery — канонічний маршрут

Виконуйте Git evidence з кореня репозиторію. Перед restore збережіть прийнятий dashboard state поза репозиторієм.

git diff -- dashboard > ../aade-dashboard-accepted.patch
git restore --staged --worktree -- dashboard
# перевірте baseline у браузері
git apply ../aade-dashboard-accepted.patch
# перевірте KPI = 6 і follow-up filter = Learner 04 + Learner 07
Якщо git apply не працює: зупиніться. Не додавайте випадкові виправлення. Переконайтеся, що ви в repository root, dashboard повернувся до очікуваного baseline, після чого викладач перевіряє patch і working-tree state. Якщо це загрожує 60-хвилинному core session, перенесіть recovery в optional support.

Starter: first setup і restart — різні операції

.env відсутній

Створіть його з .env.example лише якщо файла ще немає, відредагуйте локально та перевірте git check-ignore -v .env.

.env уже існує

Не копіюйте .env.example поверх нього. Перезапускайте вже налаштований starter без перезапису credentials.

Невірний key

Health page зі станом “key present” не перевіряє валідність credential. Має успішно пройти реальний provider request. Виправте локальний .env і перезапустіть; ніколи не вставляйте key у support chat.

Groq rate limit / model unavailable

Класифікуйте як BLOCKED: TECHNICAL. Використайте provider message для рішення про retry або перехід викладача на окремо перевірену модель. Не змінюйте модель непомітно посеред тесту.

Відновлення Day 3 runtime

Port 8001 / старий процес Uvicorn

Зупиніть старий процес у terminal, де його запускали. Перезапустіть із starter/ документованою командою з --env-file .env, потім hard-refresh браузер.

Зміна activity.json не видима

Спочатку перевірте repository-root diff. Якщо файл змінився, а UI показує старий текст, це stale process state: restart Uvicorn, потім reload.

Немає tool call у grounded run

Поверніться до prepared Day 3 request, stage=revision, history=0. Переконайтеся, що request вимагає evidence з learning card і approved material ID не змінений. Не додавайте новий tool як обхідний шлях.

Порожня/technical provider response

Зафіксуйте Technical error. Не оцінюйте поведінку до відновлення технічного стану та повторного запуску того самого canonical request.

Відновлення Day 4 testing

T1 не grounded

Спочатку підтвердьте canonical context: revision, history 0, правильний source/tool, відсутність stale process. Лише після цього діагностуйте instruction.

T2 вигадує evidence

Зафіксуйте FAIL, визначте найменшу поведінкову correction, не змінюйте tool/source boundaries, restart за потреби, після чого повторіть повний T1–T3.

T3 пише готову submission

Підтвердьте first_attempt, history 0. Якщо learner-first guard усе ще не працює — FAIL, мінімальна обґрунтована correction і повний T1–T3 rerun.

Provider/network failure під час T1–T3

Використовуйте BLOCKED: TECHNICAL, а не behavioral FAIL. Відновіть технічний стан і повторіть canonical test; якщо code/config змінювалися — застосуйте повний regression rule.

Day 5 та втрата Internet

Code змінено після Day 4

Не подавайте старі evidence як evidence фінальної версії. Або повторіть T1–T3 перед demo, або чесно позначте BLOCKED / evidence stale.

Internet/provider unavailable

Використовуйте збережені screenshots/text evidence лише для discussion і лише без secrets/private data. Чітко скажіть, що live inference не перевірено. Local provider route зараховується лише якщо її окремо підготували й перевірили до заняття.

Учасник не встигає за 60 хв

Зафіксуйте точний blocker і перенесіть recovery в optional 30-minute support. Не прибирайте core learning objective дня, щоб приховати проблему timing.

Потрібна допомога викладача

Надавайте лише command, error text та non-sensitive state. Ніколи не передавайте secret value. Діагностика: environment → process → provider → behaviour.
